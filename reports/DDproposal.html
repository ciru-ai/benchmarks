Dynamic Draft Proposal

Dynamic Draft is a server-side policy layer for llama.cpp speculative decoding. It selects draft settings from the actual tokenized prompt length, so clients do not have to guess whether a request should use short-context or long-context MTP behavior.

The Proposal

Speculative decoding already has the low-level machinery needed to accelerate generation: draft depth, draft acceptance thresholds, and MTP draft paths. The missing layer is a practical serving policy. A static setting can be good at 4k context and poor at 128k or 256k context, while external clients often cannot know the final prompt token count after chat templating and server-side formatting.

Dynamic Draft moves that decision into the server. After tokenization and before generation, the server reads the exact prompt token count, applies a configured breakpoint policy, and sets the request's speculative parameters.

0:n4,p0.25;49152:n4,p0.0;98304:n2,p0.0

One-sentence claim

Dynamic Draft makes context-conditioned speculative decoding executable and auditable inside the runtime instead of asking every client or user to manually infer draft settings per request.

Reasoning

Problem Static knobs One server-wide speculative profile is too blunt for prompt lengths ranging from 4k to 256k.
Observation Context shifts The best observed draft behavior changed between short and long prompts on Qwen 3.6 35B.
Mechanism 0-1 us Persisted DD rows measured policy decision overhead at 0-1 microseconds.
Core reasoning: the server is the only place that reliably sees the final tokenized prompt. Therefore, the draft policy should run after tokenization, not in a model card footnote or in client-side guessing logic.

Design

  1. Tokenize the request. The prompt length is counted after server-side formatting and tokenizer behavior are applied.
  2. Select a breakpoint rule. The last rule whose lower bound is less than or equal to the prompt token count is selected.
  3. Clamp to allocation caps. DD can lower draft depth per request but cannot exceed the server's configured draft allocation.
  4. Respect explicit overrides. Request-level speculative.* fields win unless the server is launched with a force policy.
  5. Record the decision. Generation metadata includes whether DD applied, the reason, prompt tokens, selected settings, and decision time.

Evidence From Qwen 3.6 35B

The benchmark used corpus-backed prompts trimmed by live tokenization. Every row generated 2048 tokens with prompt caching disabled. The static comparison below holds one measured long-context draft setting, n2,p0.0, constant across every row where it was measured, then compares it to the tested DD policy row for the same context.

Context Static draft Static TG DD policy draft DD TG Delta Readout
64k n2,p0.0 74.85 tok/s n4,p0.0 58.96 tok/s -21.2% The tested DD breakpoint was too aggressive at this context.
128k n2,p0.0 54.61 tok/s n2,p0.0 52.95 tok/s -3.0% DD selected the same static setting class and landed near parity.
256k n2,p0.0 33.51 tok/s n2,p0.0 35.82 tok/s +6.9% DD selected the same static setting class and remained strong at the near-limit prompt.
Interpretation: this run does not show that the tested DD policy is already the best possible policy at every context. It shows why the policy belongs in the runtime: once calibrated, the server can apply the intended draft setting from the exact tokenized prompt length instead of forcing one static setting onto every request.

Limits

64k is not settled. One early explicit n4,p0.0 row reached 87.94 tok/s, but a post-DD repeat on the same final-policy server reached 59.63 tok/s and matched the DD row at 58.96 tok/s. That means DD overhead was not responsible, but the 64k breakpoint should not be published as final without repeated calibration.

DD also does not discover an optimal policy by itself. The mechanism is general, but the policy must be measured per model, quantization, backend, and workload. The tested policy is evidence for Qwen 3.6 35B on this serving stack, not a universal MTP default.
